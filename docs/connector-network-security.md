# Connector network security

The HubSpot, QuickBooks, Odoo and Google Sheets HTTP transports refuse redirects. The CRM/ERP base URL must be HTTPS, use a DNS hostname rather than an IP literal or single-label hostname, and contain no credentials, query or fragment. Localhost and plain HTTP are not supported, even for development or self-hosted Odoo. The original hostname remains in the request for TLS certificate verification and SNI.

At connection time, a dedicated HTTP dispatcher resolves the hostname and rejects the whole answer set if any address is non-public or special-use (including private, loopback, link-local, multicast, IPv4-mapped IPv6 and tunnel/translation ranges). Only the checked answers are passed to the socket. Each new connection is checked again; an existing validated connection can be reused. This blocks common DNS-rebinding and redirect-to-internal attacks without a separate DNS preflight that could be bypassed on a second lookup. IP classification relies on `ipaddr.js`; review special-use ranges and keep the dependency current. Requests to names that resolve to both public and private addresses fail closed. Public IP literals are also intentionally rejected.

## Deployment implications

Existing connectors pointing at localhost, private IPs, internal DNS names, HTTPS IP literals or redirecting endpoints will stop working. Do not work around this by disabling TLS verification, modifying the transport, or injecting a custom fetch implementation. Configure an approved public HTTPS endpoint with a valid certificate and no redirect, and verify it against the vendor's actual sandbox before deployment. There is no per-tenant or environment switch allowing private HTTP targets. This is an intentional compatibility break; private installations need a separately designed, isolated and policy-controlled connector execution environment.

This is not a complete SSRF boundary for the platform. PostgreSQL and MySQL connectors still accept configured database hosts and can connect to internal services. SQLite and CSV connectors can access server filesystem paths. The global HTTP guard does not protect other code paths or custom test fetch implementations. Outbound firewall/network controls, process isolation, least-privilege filesystem permissions and restricted connector administration are still required; do not expose these connectors to untrusted tenants as a security boundary. Host firewalls must account for NAT, proxies, split-horizon DNS and custom routing: an address classified as public can still route internally in some deployments. IP classification cannot substitute for infrastructure-level egress policy. Existing connector sandboxes and production network configuration have not been validated by these tests.
