## Assessment pass 2 (2026-11-17)

`DEC-011`, `DEC-020`, `DEC-021`, `DEC-024`, `DEC-027`, `DEC-032`, `DEC-033` and `DEC-034` moved from
"not assessed" to a bounded code assessment using the files cited in each row. Two observations are
recorded without new findings: `TRUST_PROXY` defaults to true, which is safe only behind a trusted
proxy chain (R19 owns deployment); and the legal pack is served from a runtime directory
(`LEGAL_DIR`, `/app/legal` in the image), so the served text and the recorded acceptance version are
operated artifacts rather than build-time invariants (R20/owner). No decision text, status or
exception was changed. Several decisions remain "partially honoured" here because their runtime and
operational halves belong to other reviewers.

## Assessment pass 3 (2026-11-17)

All 34 decisions now carry a bounded code assessment; none remains "not assessed". Thirteen rows
moved to a definite verdict in this pass (DEC-001, 002, 004, 005, 009, 012, 014, 018, 019, 022, 023,
025, 030). Three of those are recorded as honoured rather than partially honoured (DEC-018, DEC-019,
DEC-022) because the code does exactly what the decision says and the outstanding work belongs to
other reviewers' release evidence.

Two observations from this pass are recorded rather than raised as new findings:

- **DEC-004**: a historical extraction row is deserialised with the current schema (`worker.ts:427`),
  so a record written under an older UDM version can fail on read. That is a versioning-policy gap for
  R03/R04, consistent with ARC-050's provenance finding.
- **DEC-030**: the reset URL is returned in the response body outside production
  (`auth-service.ts:624-630`). That is intended for development, but it means the "API never confirms
  an account exists" property depends on `NODE_ENV` being set correctly, which is a deployment control
  for R19 rather than a code defect.

No decision text, status or exception was modified; the historical record and its implementation
notes are untouched.
