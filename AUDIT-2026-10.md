# Audit — 2026-10 — completeness, security, privacy and the clickable surface

**Scope:** the whole repository at `main` + this branch, reviewed as an entrepreneur, a lawyer, an end
user, a buyer's procurement reviewer, an administrator and a security engineer.
**Method:** read every route, screen, document and configuration key; ran `npm run verify`,
`npm audit`, the legal validator and a full `migrate → seed → dev` cycle; clicked through every control
in the desktop renderer and the mobile screens in the test harness.
**Verdict:** the product is feature-complete against `PRD.json`, but it was not deployable as a
business. It had no privacy policy, no terms, no way to recover a forgotten password, no way for a
person to get their data out or have it erased, and nothing that enforced the retention periods the
security docs promised. Those are fixed in this pass. What is left is listed in §4 with an owner and
an honest cost.

> This document is an engineering audit, not legal advice. The legal pack under [`legal/`](legal/)
> is a draft written from what the code actually does, and needs review by a Ugandan advocate before
> it is relied on commercially.

### 1.1 What was checked and found _correct_

Recorded so the next person does not redo it:

- **Sign-out.** Desktop clears the keychain-backed token file and drops to the sign-in screen; the
  refresh token is revoked server-side. Mobile does the same through the bridge. No path left an
  access token usable after "sign out" beyond its documented ≤ 15-minute life.
- **Dead controls.** Every button, link and menu entry in the desktop renderer and the mobile screens
  does something. There are no `href="#"` placeholders, no "coming soon" dialogs, no disabled-by-accident
  primary actions, and no route that renders a blank screen.
- **Tenant isolation.** Every repository query is scoped by `organisation_id`; the new `/me/export`
  and `/me/erase` routes were written the same way and are covered by `test/privacy.test.ts`.
- **Path traversal.** `/legal/{slug}` matches a fixed allowlist (`privacy|terms|dpa|subprocessors|security`);
  `..%2F..%2Fpackage.json` returns 404 (`test/web-surface.test.ts`).
- **Secrets.** No credential, token or key material is committed; the CI secret scan passes. Password
  hashes are Argon2id at OWASP parameters, refresh tokens rotate, and API keys are stored hashed.
- **Typos.** The English and French catalogues are clean. Two Swahili strings were suspected and turned
  out to be correct (`mashine`, `kumbukumbu chache`) — recorded here so the claim is not reopened.

## 3. Perspective: what each reader would still ask for

**As the entrepreneur.** The product can now be bought: there is a contract, a policy, a security
summary and a DPA to sign. The missing commercial piece is **pricing and a click-to-accept flow** —
today the terms are published but nobody is asked to accept them at registration. Add an "I accept
the Terms and the Privacy Policy" checkbox with a stored acceptance record (who, when, which version)
before the first paid contract. It is a one-table change and it is the difference between a contract
that exists and a contract you can prove.

**As the lawyer.** The pack covers Uganda's Data Protection and Privacy Act 2019 (registration of
controllers, data-subject rights, breach notification to the Authority within 72 hours) and is written
to be GDPR-shaped so an EU customer can sign the same DPA. Three things need a human: the company
details are placeholders; the **retention of audit entries (24 months)** and **documents (90 days)**
must match the customer's own statutory duty, which varies by sector; and the **liability cap** in
`TERMS.md` §9 is deliberately conservative — set it against the contract value before the first deal.
Acceptance is not recorded anywhere; see the previous paragraph.

**As the end user.** Forgot password works, "sign out everywhere" works, and "download my data" gives
a readable JSON file. The remaining friction: the reset link in production has to be delivered by the
operator (there is no mail transport yet), and erasure is refused while you are one of several owners
— both are stated in the UI, but a user will still email support about them, so the support playbook
should answer them first.

**As the client's procurement reviewer.** They will ask for: a DPA (present), a sub-processor list
(present), a security summary (present), a penetration test (absent), SSO/SAML (absent), MFA
(absent), an audit-log **export** (the log is viewable and filterable in Settings, but there is no
button to download it — a reviewer will ask for a CSV), a SOC 2 or ISO 27001 report (absent). The
first three buy time; **MFA is the one that loses deals now**. It is also the cheapest of the four.

**As the administrator.** Retention can be set per organisation and is now enforced; the sweep is
logged. What an admin still cannot do: see _why_ a purge deleted something (the report is a count, not
a list), export the audit trail to a file, or be told when the last sweep failed. A failed maintenance
step is a `warn` line in the log and nothing else.

**As the cybersecurity engineer.** The baseline is sound: Argon2id at OWASP parameters, rotating
single-use refresh tokens, hashed API keys, per-organisation scoping, content sniffing on upload,
rate limits on the sensitive endpoints, no secrets in the tree, and now the standard header set. The
gaps that matter, in order: **no MFA**, **dependency debt** (`zod` 3 carries a high advisory and the
migration to 4 is a breaking change), **in-process rate limiting** (per-process counters reset on
deploy and do not coordinate across replicas), and **no alerting** — the access log exists, but nobody
is woken by it.

## 4. Residual risk, ranked

### 4.1 No multi-factor authentication — **medium**, next security pass

Passwords are the only factor. TOTP over `otplib`-style HMAC is roughly a day of work if recovery
codes and the "I lost my phone" path are done properly; anything less is a lockout generator. Until
then, `TERMS.md` should not promise MFA and sales should not imply it.

### 4.2 Dependency debt — **medium**, scheduled

`npm audit` reports 9 advisories (1 critical, 2 high, 6 moderate). Every one is in a transitive or
build-time package, and none is known-exploitable through this product's own request path — but that
is a statement about today:

- `zod` 3.25 (high) — used for **every** request schema. The advisory is memory exhaustion on
  oversized constrained collections; `MAX_REQUEST_MB` caps the input, which is a mitigation, not a
  fix. The fix is zod 4, a breaking migration (error shape, `record`, `.strict()` semantics) that
  touches `packages/shared` and every route. Do it as its own pass, behind the existing tests.
- `shell-quote` (critical, build tooling), `image-size` (high, Electron packaging), `esbuild`,
  `exceljs`/`uuid`, `query-string` (moderate) — all dev/build. Upgrade on the next dependency refresh.
- Add `npm audit --omit=dev --audit-level=high` to CI **after** zod 4, not before, or CI goes red for
  a known-and-accepted reason and stops being read.

### 4.3 Rate limiting and proxy trust — **medium**, small

`trustProxy` is on unconditionally, which is correct behind the documented nginx/Caddy layer and
wrong if the API is ever exposed directly (a client can then forge `X-Forwarded-For` and dodge per-IP
limits). Make it a config flag (`TRUST_PROXY`, default on) and say so in `ENVIRONMENT.md`. Per-account
limits already back up the per-IP ones, which is why this stays medium.

### 4.4 Release mechanics — **medium**, operations

Still missing: a `Dockerfile` and a publish job; `npm run db:backup` (`VACUUM INTO`) and a rehearsed
restore; `/metrics` (queue depth, job outcomes, latency) — the access log now covers the request side
only. These are the items in `DEPLOYMENT.md` §11 that are not struck through.

### 4.5 Product gap carried forward — `CON-002`

No OAuth consent flow and no refresh for Google Sheets: a Sheets destination works for about an hour
per pasted token. Recorded as a `verification` block in `PRD.json`; unchanged by this pass.

## 5. How to check this document

```bash
npm run verify          # typecheck, lint, PRD/OpenAPI/packaging/legal contracts, 376 tests
npm run test:legal      # placeholders, retention figures and sub-processor agreement
npx jest --config jest.config.cjs --selectProjects backend -t "password recovery|privacy|maintenance|HTTP surface"
git grep -n "\[COMPANY NAME\]" legal/   # every placeholder that must be replaced before launch
```

The privacy policy's retention numbers are asserted against `apps/backend/src/config.ts` by
`test:legal`, so a future change to a default fails CI instead of silently contradicting the policy.
